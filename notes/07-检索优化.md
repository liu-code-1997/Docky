# 07 · 检索优化(M5)

M4 诊断出瓶颈在检索层。M5 用消融实验(ablation)逐个尝试改进,每个都做成独立开关,
逐个评估看孤立贡献。三个方向:①markdown 切分 ②查询改写 ③重排。

本篇也是全项目**方法论教训最密集**的一篇——多个"想当然"被数字推翻。

## ① markdown 切分 + 噪声过滤

### 动机
baseline 用字符硬切(chunk_text),M4 验证过:问"路径参数",召回 Top-4 全是
"FastAPI Cloud 赞助""Conf 会议"等营销噪声块,正确文档进不来。假设:按 markdown
标题结构切 + 过滤噪声,能让正确正文浮上来。

### 实现(chunk_markdown)
- 按 `#`~`######` 标题切段,每段是语义完整的正文。
- 过滤两类垃圾:①噪声段(标题/正文含 sponsor/FastAPI Cloud/Conf/Deploying 等);
  ②HTML 样板段(按"标签密度"判定:标签+图片数相对实义字符过多即丢弃)。
- 超长段退回字符窗口切。

### 三个被数字推翻的"想当然"

**坑A:给每块加标题前缀,以为能补上下文,实测反而拉低命中。**
最初每块前缀标题链(如 `FastAPI > Path Parameters`)。结果 hit@4 从 baseline 的
50% 掉到 25%。cosine 探针发现:文档标题含高频词 "FastAPI",导致 index.md 的碎块
对任何含 FastAPI 的查询都虚高相似度(0.72+),霸占 Top-4。**去掉前缀后回升到 38%。**
教训:标题前缀是双刃剑,当标题含高频词、且查询跨语言(中文问/英文档)时弊大于利。

**坑B:设计文档被灌进知识库。**
spec 写在 docs/superpowers/specs/,而 ingest 灌整个 docs/,把项目自身文档也向量化了。
解法:把 specs 移出 docs/(docs/ 回归"纯知识库"语义)。教训:知识库目录不能混入项目文档。

**坑C(最重要):样本太少,分数差异是噪声,差点据此下错结论。**
在 8 条样本上 char=50% vs markdown=38%,险些判定"markdown 更差、放弃"。
把评估集扩到 18 条可答样本后,结论**反转**:markdown=44% > char=39%。
8 条时每条命中值 12.5%,一两条抖动就淹没真实差异。
教训:**样本少时别信分数;下结论前先把评估集做大。** 这正是评估驱动开发的核心纪律。

### ① 结论
markdown 切分(去前缀 + 噪声/HTML 过滤)在 18 条评估集上 hit@4 略优于 baseline
(44% vs 39%)。作为可选策略保留,`CHUNK_STRATEGY=markdown`(改后需重新 ingest)。
提升幅度不大,说明"切分"不是唯一瓶颈,②③仍有空间。

## ② 查询改写(QueryRewriter)

### 动机
问题是中文、文档是英文,embedding 跨语言匹配吃亏。假设:检索前先让 LLM 把问题里的
概念扩展出英文术语,拼到原问题一起检索,能提高召回。

### 实现(LlmQueryRewriter)
- 复用现有 LLM 接口:prompt 让模型只输出问题的英文关键词。
- 拼回原问题保底:`"{英文扩展} {原问题}"`。即便改写跑偏,原词仍在,最坏不劣于不改写。
- retrieve/pipeline 加可选 `rewriter` 参数;`QUERY_REWRITE=true` 或 `--query-rewrite` 开启。默认关。
- 改写示例:"FastAPI 里路径参数怎么声明?" → "path parameters declaration FastAPI FastAPI 里路径参数怎么声明?"

### ② 结论:这是 M5 最大的胜利

18 条可答样本,纯检索 hit@4:

| 切分 | 改写 OFF | 改写 ON |
|---|---|---|
| char | 39% | **94%** |
| markdown | 44% | **94%** |

- 查询改写把 hit@4 从 ~40% 拉到 **94%**,MRR 从 ~0.3 到 ~0.82。可复现(temperature=0)。
- **跨语言才是真正的头号瓶颈**,远比切分重要。中文问 / 英文档,不改写就是在跟 embedding
  的跨语言弱点硬碰。
- **改写一旦生效,切分策略的差异被抹平**(char/markdown 都到 94%)——正确文档都能召回后,
  切分的细微差别不再是瓶颈。
- 端到端(含生成):char+改写 拒答从 16/22 降到 9/22,生成分 0.16→0.27。检索准了,能答的明显变多。

**教训**:优化前先找主瓶颈。我们一开始盯着"切分"(①只带来 5pt),真正的杠杆是跨语言(②带来 50pt)。
消融实验让我们没有在次要因素上浪费更多时间。

## ③ 重排(Reranker)

### 动机
先召回较多候选(top_k×factor,默认 20),用 LLM 对每个候选打相关性分(0–10),重排取前 top_k。
目的:把向量检索排在 4 名开外、但其实相关的块提到前面。

### 实现(LlmReranker)
- 复用 LLM,逐候选打分;retrieve 有 reranker 时先召回 top_k×rerank_factor 个再重排。
- `RERANK=true` / `--rerank` 开启。默认关。代价:每问 top_k×factor 次 LLM 调用,很慢。

### ③ 结论:有效,但与改写不叠加(如预判)

完整 2×2 消融矩阵(char 库,18 条可答,hit@4 / MRR):

| | 重排 OFF | 重排 ON |
|---|---|---|
| 改写 OFF | 39% / 0.278 | **83%** / 0.657 |
| 改写 ON  | **94%** / 0.833 | 94% / 0.801 |

- **单独重排**(改写关):39%→83%,大幅有效。说明正确块大量在 top-20 里、只是排在 4 名外,重排能提上来。
- **叠加在改写之上**(改写已 94%):hit@4 纹丝不动,MRR 反而略降(0.833→0.801)。
  改写已把正确块送进 top-4,重排无更多可提;重新打分偶尔还把最优项挪开。

**关键洞察**:改写与重排是通往同一目标(正确块进 top-4)的两条路,**不叠加**。
改写更优:更快(1 次 LLM 调用 vs 重排 ~20 次)、效果更好(94% vs 83%)。

## M5 总结与推荐配置

消融实验(纯检索 hit@4,18 条):

| 手段 | 单独效果 | 成本 | 推荐 |
|---|---|---|---|
| ① markdown 切分 | 39%→44% | 免(重灌库一次) | 可选,提升有限 |
| ② 查询改写 | 39%→**94%** | 每问 +1 次 LLM | ✅ **强烈推荐** |
| ③ 重排 | 39%→83% | 每问 +~20 次 LLM | 仅当无法改写时的替代 |

**最终推荐**:开 ②查询改写(主力),①markdown 可叠加(便宜),③重排在有②时不必开。
`QUERY_REWRITE=true`(+可选 `CHUNK_STRATEGY=markdown`)。

**方法论收获**:优化前先用评估找主瓶颈。我们从"切分"入手(直觉),但数字证明真正的杠杆是
"跨语言查询改写";②③殊途同归而不叠加,靠 2×2 消融才看清。没有评估,极可能同时开三个、
既慢又以为"都在起作用"。

## ④ embedding 前缀(M8;被数字否决)

### 动机
nomic-embed-text 官方推荐给查询加 `search_query:`、给文档加 `search_document:` 前缀。
M8 把前缀纳入 profile,本以为是"低成本白捡的提升",用 M7 评估地基验证。

### 受控 A/B(同一 char 切分、同一评估集,各自删库重灌,只差前缀)

| 指标 | 前缀开 | 前缀关 |
|---|---|---|
| hit@4 | 88.9% | **94.4%** |
| recall@4 | 0.889 | **0.944** |
| precision@4 | 0.583 | **0.597** |
| nDCG@4 | 0.773 | **0.822** |
| MRR | 0.741 | **0.792** |
| 拒答正确率 | 81.8% | 72.7% |

### 结论:回滚
前缀在**所有检索指标**上都更差,故 tech.toml 前缀清空(回滚)。推测:本地语料是中文问/英文档的
跨语言场景,且已用查询改写扩英文术语;nomic 前缀是为英文 query→英文 doc 调的,叠加到这个
链路上反而干扰。

### 方法论收获(最重要)
"官方推荐"+"听起来该有用" ≠ 真的有用。**M7 评估地基在这里第一次兑现价值:拦下了一个照直觉
会合进去的检索退化。** 前缀机制仍保留在 profile 里(换英文语料/换模型时可再开、再用 eval 验),
只是 tech 默认关。

## ⑤ 多路召回 dense+sparse+RRF(M9;被数字否决)

### 动机
稠密向量对**精确术语**(`item_id`/`LEFT JOIN`/`query_points`)未必命中。加一条稀疏(BM25 式词形)
召回,用 Qdrant 原生 RRF 融合两路,期望抬升 recall。稀疏向量纯 Python 自算(crc32 稳定哈希,
零依赖),`Modifier.IDF` 服务端加权。

### 受控 A/B(同一 dense+sparse 库,52 正例含 5 道多来源,只切 hybrid 开关)

| 指标 | hybrid 关(dense) | hybrid 开(RRF) |
|---|---|---|
| hit@4 | **94.2%** | 92.3% |
| recall@4 | **0.936** | 0.907 |
| precision@4 | **0.567** | 0.562 |
| nDCG@4 | 0.823 | 0.823 |
| MRR | 0.796 | **0.801** |
| 拒答正确率 | 78.6% | **85.7%** |

### 结论:默认关
稀疏路让 **recall/hit/precision 反降**。推因:本地是**英文小语料**,查询已经过改写补了英文术语,
稠密路本就够强;RRF 把"词形相似但相关性更低"的块拉进前列,挤掉了好的稠密命中。naive BM25
(crc32 哈希、无参数调优)在这里是噪声 > 信号。

### 方法论收获
又一次"听起来该有用"被数字推翻(继 M8 前缀之后)。**hybrid 机制完整保留**(命名向量 + RRF 全通,
换大语料/多语种时可再开、再用 eval 验),但 tech 默认 `HYBRID=false`。M9 的净产出不是"更好的检索",
而是"**一条随时可启用、且已被证明当前无益**的召回路"——以及再次确认评估地基能挡住想当然。

## ⑥ Listwise 重排(M10;有得有失,净正向)

### 动机
旧 `LlmReranker` 逐条打分(N 次调用/查询,慢)。M10 加 `ListwiseLlmReranker`:一次 LLM 调用对
全部候选排序,零依赖;并经 `build_reranker` 工厂 + `rerank_provider` 配置可插拔(将来接 bge
cross-encoder 只需加一类一分支,retrieve/pipeline 不动)。诊断已示重排 ROI 有限,但可能救排序题。

### A/B(同库,rerank 关 vs 开 listwise)

| 指标 | 关 | 开(listwise) |
|---|---|---|
| hit@4 | 94.2% | 94.2% |
| recall@4 | **0.936** | 0.926 |
| precision@4 | **0.567** | 0.534 |
| nDCG@4 | 0.823 | **0.839** |
| MRR | 0.796 | **0.817** |
| 生成分 | 0.609 | **0.683** |
| 拒答正确率 | 85.7% | **87.5%** |

### 结论:默认关,但确实提质
重排把相关块**排得更靠前**(nDCG/MRR↑),更好的上下文进前排 → **生成分明显↑(+7.4%)**;代价是
从 20 候选选 4 时偶漏 dense 本命中的(recall/precision 微降)+ ~2-3x 延迟。**净正向**,是继 M11
之后第二个真有效的优化,也印证诊断:重排帮的是**排序+下游生成**,不是召回。

`rerank` 默认仍关(延迟+recall 微降,保守);`rerank_provider` 默认 `llm_listwise`(优于旧 pointwise),
`RERANK=true` 即启用——一个"质量↑/延迟↑"的按需旋钮。**bge cross-encoder 扩展点已留好**(见工厂)。

## ⑦ M11 补齐:多查询 / 上下文排序 / 行内引用

三开关默认关,eval 逐个量(对照 baseline hit 94.2 / recall 0.936 / nDCG 0.823 / MRR 0.796 / gen 0.609 / refusal 85.7):

| 开关 | hit@4 | recall@4 | nDCG@4 | MRR | 生成分 | 拒答正确率 |
|---|---|---|---|---|---|---|
| baseline | 94.2 | 0.936 | 0.823 | 0.796 | 0.609 | 85.7 |
| **+multi_query** | **98.1** | **0.974** | **0.871** | **0.856** | **0.658** | **89.3** |
| +reorder | 94.2 | 0.936 | 0.823 | 0.796 | 0.641 | 87.5 |
| +inline | 94.2 | 0.936 | 0.823 | 0.796 | 0.582 | 85.7 |

### 多查询(multi-query):全项目最强单项 ✅
recall 0.936→**0.974**、hit 94→**98**、nDCG/MRR/生成/拒答全升。生成多个查询变体各自检索、客户端 RRF
融合,**多捞回了相关文档**——救回了诊断里的漏召回题(如"图数据库插入点")。这印证:此前 M8/M9 检索
优化被否,不是"检索没救",而是**方法不对**;多查询这种"扩语义覆盖面"的手段才对症。代价:每问多 1 次
扩展调用 + N 次检索(慢)。**强烈推荐;默认仍关(延迟,同 rerank 的处理),`MULTI_QUERY=true` 启用。**

### 上下文排序(reorder):免费的小正向
把最相关块放上下文两端。检索指标按设计不变(**度量教训**:一开始误把 reorder 后的列表也拿去算
mrr/ndcg,会机械拉低——已修成"评估用 reorder 前列表、reorder 只喂生成")。生成 +0.032、拒答 +1.8,
且**零额外 LLM 调用**。安全可开,默认关。

### 行内引用(inline):指标测不出的 UX 特性
生成分反降 0.609→**0.582**。不是变差——让 LLM 标 [1][2] 会微调措辞、命中的关键词变少,而 **keyword
评分器无法给"引用可信度"计分**。这是评分口径的局限,不该据此判它差。默认关,作为可信度/UX 开关保留。

### 方法论收获
同样"补检索",multi_query 大赢而 M8 前缀/M9 hybrid 被否——差别在**是否扩大语义覆盖**(多查询)vs
仅换词形匹配(BM25/前缀)。选对手段比"要不要优化检索"更重要;而选得对不对,仍是 eval 说了算。

## ⑧ bge 专用 cross-encoder 重排(M10 补齐;最强重排)

M10 先做 listwise、留了 cross-encoder 扩展点;本轮实装 `bge-reranker-v2-m3`(sentence-transformers,惰性加载,不用则不引 torch)。

### A/B(同库 144,rerank 关 vs bge;对照 listwise)

| 指标 | 关 | **bge** | listwise |
|---|---|---|---|
| hit@4 | 94.2% | **100%** | 94.2% |
| recall@4 | 0.936 | **0.974** | 0.926 |
| precision@4 | 0.567 | **0.611** | 0.534 |
| nDCG@4 | 0.823 | **0.936** | 0.839 |
| MRR | 0.796 | **0.926** | 0.817 |
| 生成分 | 0.609 | 0.644 | 0.683 |
| 拒答正确率 | 85.7% | **94.6%** | 87.5% |

### 结论:bge 是最强重排,但按需启用
从 recall_k=20 候选里挑出明显更好的 top-4——hit 100%、nDCG 0.823→**0.936**、MRR 0.796→**0.926**,
precision/recall/拒答全升,排序质量远超 listwise。代价:引 torch(~GB)+ 首次下模型 2.3GB + CPU 逐对打分慢。
**决策**:rerank 默认仍关(延迟);`rerank_provider` 默认保持 `llm_listwise`(零依赖免 torch);
bge 作为**最高质量**选项按需开(`RERANK=true RERANK_PROVIDER=cross_encoder`)。

### 方法论收获(诚实修正)
此前一再判断"多查询后检索近顶、bge ROI 有限"——**被数据推翻**:bge 对排序(nDCG/MRR)提升巨大。
再次印证全篇主线:**别信先验(哪怕是自己的),以 eval 为准。**
